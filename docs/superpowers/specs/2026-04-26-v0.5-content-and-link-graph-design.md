# v0.5.0 — Near-duplicate content detection + Internal link graph

**Date:** 2026-04-26
**Status:** Approved, pending implementation plan
**Target version:** v0.5.0

## Goal

Add two cheap-local-analysis passes that surface high-value findings using crawl data already collected. Both default-on with opt-out flags, both ship in the same v0.5.0 release.

1. **Near-duplicate content detection** (MinHash): clusters of pages with ≥0.85 Jaccard similarity over their body text. Flagship use case: e-commerce / programmatic-SEO / multi-location service sites where templated content masks thin uniqueness.
2. **Internal link equity** (PageRank): per-page link-equity scores plus the "underlinked important pages" finding (high content, low rank — the Sitebulb-style "your money page gets 1 internal link, your contact page gets 200" insight).

Both are pure analyses on existing `PageReport[]` data — no new crawls, no external APIs, no new top-level dependencies.

## Non-goals

- No tunable parameter flags (Jaccard threshold, PageRank damping, etc.). Hardcoded defaults match SEO-tool conventions; tuning is YAGNI for v0.5.
- No anchor-text analysis on the link graph. PageRank score per page is the v0.5 deliverable; anchor-text breakdown is a v0.6+ candidate.
- No per-cluster boilerplate detection (which content within a cluster is shared vs. unique). Surface the cluster; let the consultant inspect manually.
- No "fix this" suggestions on near-duplicate clusters beyond the generic recommendation. Per-cluster remediation depends on the user's CMS, canonicalization strategy, and content goals.
- No graph community/cluster detection. Top-N PageRank list is the v0.5 surface; community detection is v0.6+.

## Decisions

| # | Question | Decision |
|---|----------|----------|
| 1 | Default-on vs opt-in | Default-on with opt-out flags (`--no-content-dedup`, `--no-link-graph`). Matches existing default-on cheap-analysis pattern. |
| 2 | MinHash output shape | Cluster-based summary in `report.contentDedup` + per-page `CONTENT_NEAR_DUPLICATE` issue (medium severity). |
| 3 | Link graph output shape | Per-page `pageRank` field + summary highlights (`topPages`, `underLinkedImportantPages`). No per-page issue. |
| 4 | Parameter tuning | All hardcoded: Jaccard `0.85`, shingles `k=5`, PageRank damping `0.85`, `20` iterations, MinHash signatures `128`, LSH bands `16` × rows `8`. |

### Open-source upgrade considerations

The package is published to npm as `@davo20019/seo-audit` (current v0.4.0 → planned v0.5.0). The default-on additions surface on every audit. Three OSS-relevant considerations:

- **JSON shape grows additively but visibly.** New top-level `report.contentDedup` and `report.linkGraph` optional fields. New per-page optional `pageReport.linkGraph: { pageRank: number }`. All optional — v0.4 consumers ignoring unknown fields keep working. CHANGELOG documents the additions.

- **`CONTENT_NEAR_DUPLICATE` is a new medium-severity issue, which interacts with `--fail-on` cron pipelines.** A v0.4 user running `seo-audit ... --fail-on medium` daily passes today. After upgrading, if the site has any near-duplicate clusters (most e-commerce sites do), the FIRST v0.5 run may surface new failures — not because anything regressed, but because the new check is now running. **Crucial mitigation:** the fresh-mode `--fail-on` only fails on regressions vs. the previous persisted crawl (positive `severityDelta`). So Phase-3-monitoring users with at least one prior persisted crawl are unaffected — the new issues exist on both sides of the diff and net to delta=0. Only users running `--fail-on` *without* a persisted baseline (e.g., a brand-new install in a fresh CI runner) see the new findings on first run. CHANGELOG documents this explicitly with the recovery options: pass `--no-content-dedup`, raise `--fail-on high`, or run the audit once to seed a baseline.

- **No new top-level dependencies.** MinHash uses `node:crypto` (already imported elsewhere in the codebase). PageRank is plain arithmetic. Both run only on data already in memory.

### Module dependency direction

One-way, identical to existing checks: `cli → analyzer → checks/{content-dedup, link-graph} → types`. Both new check modules depend only on `PageReport[]` and `node:crypto`. No new top-level dependencies.

### Default-on integration

Both features run unconditionally inside `analyze()`. Skipping happens at the orchestrator-call level: the analyzer reads `rawOptions.contentDedup !== false` and `rawOptions.linkGraph !== false` (default-true semantics). The CLI flags `--no-content-dedup` and `--no-link-graph` set the AnalyzeOptions field to `false`, which the analyzer respects.

## Content-dedup algorithm (`src/checks/content-dedup.ts`)

### Public API

```ts
export const SHINGLE_SIZE = 5;
export const MIN_WORDS = 50;
export const SIMILARITY_THRESHOLD = 0.85;
export const NUM_HASHES = 128;
export const LSH_BANDS = 16;
export const LSH_ROWS_PER_BAND = 8;  // bands * rows = NUM_HASHES

export function buildContentDedupReport(pages: PageReport[]): ContentDedupReport;

// Exposed for low-level tests
export function tokenize(text: string): string[];
export function shingle(tokens: string[], k: number): Set<string>;
```

`buildContentDedupReport` mutates each cluster member's `page.issues` array to push the `CONTENT_NEAR_DUPLICATE` issue, AND returns the cluster summary. The mutation is a deliberate cross-cutting side effect — `buildSummary()` runs AFTER and counts the new issues into `summary.issueTotals.medium`.

### Tokenization rules

- Lowercase the body.
- Strip non-alphanumeric Unicode (keep accented chars; replace anything else with whitespace).
- Split on whitespace.
- Drop tokens shorter than 2 chars.

### Shingling

For each page's token array, build the set of all `k=5`-word k-grams. A page with fewer than 5 tokens produces an empty shingle set and is skipped (bumps `pagesSkipped`).

### MinHash signatures

For each page, compute 128 minimum hashes:

- 128 fixed salt strings (deterministic constants in the source) — `const SALTS = [...new Array(128)].map((_, i) => `seo-audit-minhash-salt-${i}`)`.
- For each hash function `i`, compute `min(hash_i(shingle))` over all the page's shingles.
- Each `hash_i` is `crypto.createHash("md5").update(salt[i] + shingle).digest("hex")`, taking the first 8 hex chars (32-bit prefix) as a uint.

Determinism is critical: same input → same signature → same clusters. The fixed salt strings ensure runs are reproducible across processes.

### LSH bucketing (sub-quadratic scaling)

Split each 128-element signature into 16 bands of 8 rows. Hash each band-slice (8 ints concatenated as a string) into a bucket. Pages whose signatures match in ANY band are candidate pairs.

Theoretical guarantee: for similarity `s`, probability of being in the same bucket in at least one of 16 bands ≈ `1 - (1 - s^8)^16`. At s=0.85, ≈98%. At s=0.50, ≈10%. So real near-duplicates are almost always candidates; non-duplicates rarely are.

This collapses the worst-case O(n²) Jaccard verification to O(n × avg_bucket_size), which is effectively linear in practice.

### Verification

For each candidate pair, compute the Jaccard similarity from the MinHash signatures: `similarity = (count of positions where signatures agree) / 128`. If `similarity >= 0.85`, the pair is confirmed.

### Clustering

Union-find over confirmed pairs. Each connected component with ≥2 members is a `ContentCluster`. Clusters are sorted by member count descending in the report.

### Representative selection

For each cluster, the representative is the member whose body has the most words. Ties broken by URL (lexicographic). The representative's `similarityToRepresentative` is `1.0`; other members report their pairwise Jaccard against the representative.

### Per-page issue

Every cluster member gets:

```ts
{
  code: "CONTENT_NEAR_DUPLICATE",
  severity: "medium",
  message: `Page is part of a ${clusterSize}-page near-duplicate cluster (representative: ${representativeUrl}).`,
  recommendation: "Review whether these pages should be consolidated, canonicalized, or differentiated. Common causes: templated content with thin unique text, scraped/syndicated content, parameter variants without canonical tags."
}
```

### Skip rules

- `bodyText === null` → skipped, `pagesSkipped` increments.
- Token count < 50 (after tokenization) → skipped, `pagesSkipped` increments.

### Edge cases

- 0-page input → empty report, no crash.
- 1-page input → no clusters (nothing to compare against).
- All pages identical → 1 cluster of N members, all similarity 1.0.

## Link-graph algorithm (`src/checks/link-graph.ts`)

### Public API

```ts
export const PAGERANK_DAMPING = 0.85;
export const PAGERANK_ITERATIONS = 20;
export const TOP_N = 10;

export function buildLinkGraphReport(pages: PageReport[]): LinkGraphReport;
```

`buildLinkGraphReport` mutates each `PageReport` to attach `linkGraph: { pageRank }`, AND returns the summary. No per-page issues are emitted — this is a pure informational layer.

### Graph construction

For each page `p`, edges `(p.finalUrl → target)` for every `target` in `p.discoveredLinks` such that:
- `target` is in the crawled set (matches some other page's `finalUrl`),
- `target !== p.finalUrl` (no self-loops).

Edge count is reported as `report.edges`. Note: discovered links to URLs not in the crawled set (external links, internal links to uncrawled paths) are silently dropped — they don't contribute to internal link equity.

### Initialization

Every page starts at `1 / N` where N is the number of crawled pages.

### Iteration

Standard PageRank update for 20 iterations:

```
pr_new[i] = (1 - d) / N + d * Σ(pr_old[j] / outDegree[j]) for j → i
```

with `d = 0.85`. Dangling pages (zero outbound internal edges) distribute their score uniformly across all pages each iteration:

```
danglingMass = sum(pr_old[j] for j with outDegree[j] === 0)
pr_new[i] += d * (danglingMass / N) for all i
```

After 20 iterations, the vector is normalized so `sum(pr) === 1.0` (corrects floating-point drift).

20 iterations converges to within `0.001` for any realistic site under 100k pages — verified empirically by the convergence tests.

### Top-N selection

`topPages`: the 10 pages with the highest `pageRank`, sorted descending. Each entry includes `wordCount` and `incomingInternalLinks` for context.

### `underLinkedImportantPages` heuristic

The signature finding. Uses median-based filtering:

```ts
const medianWords = median(pages.map(p => p.checks.wordCount));
const medianRank  = median(pages.map(p => p.linkGraph.pageRank));
const candidates  = pages.filter(p =>
  p.checks.wordCount > medianWords &&
  p.linkGraph.pageRank < medianRank
);
const top = candidates
  .sort((a, b) => b.checks.wordCount - a.checks.wordCount)
  .slice(0, 10);
```

This surfaces "lots of content, weak internal-link support" without us having to define what counts as an "important page" via external signals — the audit's own crawl data does the work.

### Edge cases

- 0-page input → `pagesAnalyzed: 0, edges: 0, topPages: [], underLinkedImportantPages: []`. No crash.
- 1-page input → `topPages` has the single entry (`pageRank: 1.0`); `underLinkedImportantPages` is empty (median filtering degenerates to `<` against itself).
- 2 pages with mutual link → both `pageRank` ≈ 0.5.
- All pages dangling (no internal links anywhere) → uniform distribution; `topPages` is just the first 10 in input order. Acceptable degenerate case.

## Output rendering

### Text formatter (`src/cli.ts`)

Two new functions, signature matching `formatGscEnrichment` / `formatGa4Enrichment`:

```ts
function formatContentDedup(r: ContentDedupReport): string[];
function formatLinkGraph(r: LinkGraphReport): string[];
```

**Content dedup text** — header line with cluster/page counts; per-cluster block with member URLs and similarity scores. Empty case: one-line "0 near-duplicate clusters" message.

**Link graph text** — header line with iteration/damping/edge counts; "Top by PageRank" list (10 lines); "Underlinked important pages" list (only if non-empty). Skip-on-1-page case: one-line "skipped" message.

Spliced into `formatTextReport` after the existing GSC/GA4 enrichment sections, before priority issues:

```ts
if (report.contentDedup) lines.push(...formatContentDedup(report.contentDedup));
if (report.linkGraph)    lines.push(...formatLinkGraph(report.linkGraph));
```

The per-page text line in `formatPage` does NOT add a PageRank field. PageRank is read via the summary lists, where it's actionable.

### HTML report (`src/report.ts`)

Two new top-level sections, ordered after Search Console / Analytics, before Priority issues / Agent Readiness:

- `<h2>Content duplicates</h2>` — summary `<p>` with cluster count and threshold; one `<details>` block per cluster (summary line "47 pages near-duplicate of …", expanded list of members with similarity scores).
- `<h2>Internal link equity</h2>` — summary `<p>` with iteration count + damping + edge count; two side-by-side tables (Top 10 by PageRank, Underlinked important pages). Each row: URL, PageRank (4 decimal), word count, incoming internal links.

`renderContentDedupSection(report.contentDedup)` and `renderLinkGraphSection(report.linkGraph)` follow the structure of existing `renderGscSection` / `renderGa4Section`. URLs HTML-escaped through the existing `escapeHtml` helper.

The Pages table (existing `renderPages`) gains an optional `PageRank` column, conditional on `report.pages.some(p => p.linkGraph)` — same pattern as the GSC/GA4 columns added in v0.3.0.

### Order of operations in `analyze()`

1. Crawl + build `PageReport[]`.
2. **`buildLinkGraphReport(pages)`** — mutates each `page.linkGraph`. Runs first because content-dedup may want to use it later (not in v0.5; reserves the option).
3. **`buildContentDedupReport(pages)`** — mutates each cluster member's `page.issues` AND returns the cluster summary.
4. GSC / GA4 enrichment (existing).
5. **`buildSummary(pages, ...)`** — counts all issues including the new `CONTENT_NEAR_DUPLICATE` ones.
6. `priorityIssues` (existing) — now also ranks dedup issues by traffic if GSC/GA4 enabled. Cross-feature win: pages flagged as near-duplicate AND with GSC traffic surface in the priority list. Existing ranker requires no changes.

## Tests

### `tests/checks/content-dedup.test.ts` (~15 tests)

A `makePage(url, bodyText, opts?)` factory at the top builds minimal `PageReport` fixtures.

**Tokenization + shingling:**
- `tokenize` lowercases, strips non-alphanumeric, drops sub-2-char tokens.
- `shingle` produces `n - k + 1` shingles for an n-token input; produces empty set for input < k tokens.

**Skip rules:**
- `bodyText === null` → skipped.
- bodyText with < `MIN_WORDS` tokens (after tokenization) → skipped.
- exactly `MIN_WORDS` tokens → included.

**Cluster construction:**
- Two identical-body pages → 1 cluster of 2 members, similarity 1.0.
- Two fully disjoint pages → 0 clusters.
- A~B (0.9), B~C (0.9), A~C (0.6) → all three in one cluster (transitive closure).
- Threshold boundary: 0.86 clusters; 0.84 doesn't.
- 50 identical pages → 1 cluster of 50 (LSH scaling sanity check).

**Representative selection:**
- Cluster of 3 with body lengths [200, 500, 100] words → 500-word page is representative.

**Issue generation:**
- Every cluster member gets `{ code: "CONTENT_NEAR_DUPLICATE", severity: "medium", ... }` pushed onto `page.issues`.
- Issue message includes the cluster size and representative URL.

**Determinism:**
- Calling `buildContentDedupReport` twice on the same input produces equal reports (same cluster order, same members).

**Empty / single-page:**
- 0-page input → empty report.
- 1-page input → 0 clusters.

### `tests/checks/link-graph.test.ts` (~12 tests)

**Graph construction:**
- 3 pages A→B, A→C, B→C → `edges: 3`.
- Self-loop `A→A` → dropped.
- A→external-url (target not in crawled set) → dropped.

**PageRank correctness:**
- 4-node directed cycle (A→B→C→D→A) → all four ≈ 0.25 (within 0.001).
- A→B, A→C, A→D (3 dangling targets) → B = C = D > A.
- Star graph (10 leaves → hub, hub dangling) → hub has the highest rank.

**Edge cases:**
- Empty input → `pagesAnalyzed: 0, edges: 0, topPages: [], underLinkedImportantPages: []`.
- Single page → `topPages` has 1 entry with `pageRank: 1.0`; `underLinkedImportantPages: []`.
- Two pages with mutual link → both ≈ 0.5.

**Per-page mutation:**
- After `buildLinkGraphReport`, every page has `page.linkGraph.pageRank` finite in [0, 1]. Sum ≈ 1.0.

**`underLinkedImportantPages` heuristic:**
- Constructed fixture of 10 pages where exactly 3 high-content pages have low PageRank → result contains those 3 sorted by wordCount desc; low-content pages with low rank excluded; high-content with high rank excluded.

**Determinism:**
- Two consecutive calls produce equal results to 0.0001 precision.

## Risks & open questions

- **Cluster-size noise on programmatic-SEO sites.** A site with 5,000 product pages all in one near-duplicate cluster will produce a single cluster entry with 5,000 members. The text/HTML rendering can show all members, which is voluminous. Acceptable: render the first 50 members with a "… and N more" indicator. **Decision:** apply the indicator at 50 members per cluster in the text formatter and HTML rendering; the underlying JSON keeps all members.
- **Determinism under floating-point drift.** PageRank iteration accumulates tiny floating-point errors. Two runs on the same input *should* produce bit-identical results, but if Node's V8 ever introduces nondeterministic FP behavior under JIT optimization, the tests would flake. Mitigation: assert `toBeCloseTo(expected, 0.0001)` rather than `toBe(expected)` in the determinism test.
- **MinHash signature collisions.** With 128 hashes × 32-bit values, the probability of two unrelated pages having identical signatures by accident is astronomically small (≈ 1 in 2^32 for any given pair under random shingles). Acceptable.
- **`--no-content-dedup` + `--fail-on` interaction documented.** Already covered in the CHANGELOG note above. No additional code path needed — the opt-out skips the entire orchestrator call, so the new issues simply don't exist.
- **Future: per-page PageRank column in text output.** Currently omitted to keep `formatPage` tight. If users start asking for it, can add as a single new line under each page entry. v0.6+ candidate.
